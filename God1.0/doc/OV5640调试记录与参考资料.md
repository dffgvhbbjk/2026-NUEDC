## 一、项目目标（最终交付）

## 二、硬件平台与引脚

- FPGA: EP4CE6E22C8 (TQFP144), 6272 LE, 无外挂 SDRAM
- 摄像头: 野火 YH-OV5640 (DVP 接口, RGB565)
- XCLK: PLL c3 输出 24MHz → cam_xclk (PIN_112)
- 上电时序: ov5640_poweron (PWDN 6ms → RST_N 8ms → SCCB 29ms)
- 传输: UART 2Mbps → CH343 → PC (Qt 上位机)
- SCCB: 250kHz, 地址 0x78, sdat 开漏

引脚详见 CLAUDE.md（不可随意更改）。

## 三、已解决的问题（按时间线）

### 1. SCCB 配置写不进去（cfg_done=0, cfg_progress=0）

**现象**：手写 SCCB 控制器不检查 ACK、STOP 时序错误（SCL/SDA 同拍跳变），配置表换多张都无效，cfg_progress 停在 0（第一个寄存器就没人 ACK）。

**解决**：换用野火官方 52_ov5640_vga_640x480 例程的 `i2c_ctrl.v`（标准 START/STOP）。但官方版"从机不应答则停住"，在本板 SDA 应答临界时卡死。

**最终解决**：去掉 ACK 卡死——应答时钟照走不检查 ACK 值（I2C 从机接收数据不依赖主机验证 ACK，照样收到写入）。cfg_done=1，258 个寄存器写入。

> ⚠️ 教训：ACK 检查在总线临界时会导致"看起来配置完成但实际没写进去"，以及"写了一半卡死"。

### 2. 图像全 0（无像素数据）

**现象**：配置写进去了但图像全 0，href_lines=0（cam_href 从未拉高）。

**分析**：这是 PCLK 太高（30fps 需 52-70MHz）超出板子接收能力 + 配置未完全生效的综合结果。

### 3. 花屏（缓冲溢出）

**现象**：有图像但完全错乱，href≈950（1280×960 的行数），行长计数饱和 65535。

**根因**：**摄像头分辨率寄存器（0x3808-0x380B=640×480）未生效，实际输出 ~1280×960**。降采样按 640 宽设计（每行 64 采样），1280 宽的线给出 80 采样/行 → 3072 字节缓冲溢出 → 花屏。

**数学证明**：帧率 11fps ÷ PCLK 28.5MHz → HTS×VTS=2.57M → 只有 1280×960 吻合；640×480 应为 15.3fps。

**解决（部分）**：降采样加 64×48 硬边界裁剪（`x_div10<64 && y_div10<48`），每帧恒 3072 采样，缓冲不再溢出。仿真验证 PASS（1280×960 和 640×480 输入均 3072 采样）。

### 4. 分辨率寄存器不生效（摄像头跑 1280×960）

**尝试过的方案**：
| 方案 | 结果 |
|------|------|
| 末尾加软复位 0x3008=0x82 | ❌ 寄存器被清回默认 → 64fps 无图 |
| 唤醒 0x02 挪到末尾（掉电期间写分辨率） | ❌ 摄像头进掉电不输出（0 帧） |
| 换官方 PLL 0x11/0x46 | ❌ 症状不变（仍 1280×960） |

**当前方案**：**采集适配摄像头实际输出**——ov5640_capture 加宽坐标到 1280×960（byte_cnt 12bit, pix_x/pix_y 11bit），downsample 改 /20 网格（×3277>>16）。让整幅场景能显示，不再依赖分辨率配置生效。

## 四、当前未解决的问题

### 核心问题：摄像头图像仍不可辨认

- 配置已写入（cfg_done=1）
- 摄像头在出流（帧率 7-11fps）
- 但画面无法辨认（有黑色像素但不成块）
- href 异常：行长计数 ~100万 PCLK（href 卡高/极性异常）

**待验证**：烧录最新固件（采集适配 1280×960 /20 后）看 href 和画面。

### 疑似根因（待确认）

1. **分辨率配置不可靠**：SCCB 写入可能部分丢失（去掉 ACK 检查后无法确认每笔写入成功），分辨率寄存器（0x3808-0x380B）未生效 → 摄像头跑默认 1280×960。
2. **href 信号异常**：行长 100 万 PCLK 说明 href 有长时间卡高，可能是采样相位/极性问题，或摄像头默认状态下的异常输出。
3. **PCLK 与板子承受能力**：板子采集逻辑按 44MHz 布线（SDC），高帧率高分辨率 PCLK 超出承受 → 同步异常、画面错位。

### 下一步排查思路

1. 烧最新固件（/20 采集）确认 href ≈ 960、画面是否可辨认。
2. 若 href 行长仍异常 → 用 **SignalTap** 抓 cam_pclk/cam_href/cam_vsync/cam_data 实际波形（Quartus 内置），确定：
   - href 是否真的卡高
   - 数据是否在 PCLK 上升沿稳定
3. 若采样相位问题 → 试下降沿采样。
4. 若分辨率配置不可靠 → 接受 1280×960，采集按 /20 适配（已做）。

## 五、关键诊断数据（最新）

```
状态字节: status=0x74/0x75
  bit0 valid, bit1 stable, bit2-3 row_hi, bit4 v2, bit5 diag, bit6 cfg_done
采集链诊断 (bit5=1 时结果字节):
  byte0-1 = href 行数/帧      (640×480→480, 1280×960→960)
  byte2-3 = 行长/64           (640宽→20, 1280宽→40; 异常时~16000=100万PCLK)
  byte4   = 配置进度 (cfg_progress)
  byte6-7 = 降采样样本数       (正常3072)

实测 (0x41/0x72 PLL):
  href ≈ 960      → 摄像头 1280×960
  行长/64 ≈ 16300 → href 卡高异常
  ds 变化大       → 降采样输出不稳定
```

### 2. OV5640 关键寄存器（来自数据手册）
```
0x3008: bit7=软复位, bit6=软件掉电, bit1=唤醒
0x3035: bit7-4=SDIV0 (系统分频), bit3-0=MIPI 分频
0x3036: PLL 倍频 (4~252), VCO 需 500-1000MHz
0x3037: bit4=PLL根分频, bit3-0=预分频
0x3108: 保持 0x01 (手册要求)
0x4300: 输出格式 (0x61/0x6f=RGB565, 0x6f=YUV422?)
0x4740: POLARITY CTRL (bit5=PCLK 极性, 默认0x20)
0x3808-0x380B: 输出分辨率 (640×480=0x0280,0x01E0)
0x380C-0x380F: HTS/VTS (帧时序)
```

### 3. PCLK 计算公式
```
PCLK ≈ (XCLK / 预分频 × 倍频 / SDIV0) / 8
VCO = XCLK / 预分频 × 倍频  (需 500-1000MHz)
帧率 = PCLK / (HTS × VTS)
官方 15fps (0x41/0x72): PCLK≈28.5MHz, 640×480≈15fps
官方 30fps (0x21/0x72): PCLK≈57MHz
官方 FPGA (0x11/0x46): PCLK≈70MHz (本板接不住)
```

### 5. 花屏常见根因（网络总结）
1. **PCLK 超驱动能力**（如某板只能 50MHz）：分辨率/帧率越高 PCLK 越高，超出→同步异常、画面被切割成多份 → **调低帧率/分辨率**。
2. **数据对齐错误**：高/低字节顺序错或采样沿偏一个周期 → 花屏。
3. **配置后需丢前 10 帧**：寄存器配完需 ~10 帧才稳定。
4. **DVP 模式下 0x3108 bit_div**：某些分辨率（1080P/1024×768）需要恢复 10-bit（0xA）。

## 七、采集链设计（当前代码状态）

```
OV5640 → ov5640_capture → downsample → uart_tx_2M → 串口
          │ 取偶数字节   │ /20 (1280×960)
          │ pix_x0-1279  │ 64×48 硬裁剪
          │ pix_y0-959   │
          ↓
          gap_detect (FPGA 检测, 待验证)
```

- **ov5640_capture**: posedge PCLK 采样, 偶数字节=RGB565 高字节(亮度), 已加宽到 1280×960
- **downsample**: ×3277>>16 实现 /20, 64×48 硬边界 (x_div20<64 && y_div20<48)
- **uart_tx_2M**: 帧头4 + 图像3072 + 结果8 + 帧尾4 = 3088B/帧, 2Mbps, DIAG_MODE=1 时结果字节携带诊断
- **i2c_ctrl**: 官方控制器, 已去 ACK 卡死
